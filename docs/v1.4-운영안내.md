# v1.4 운영 안내 (사진 복구·전송 대기)

기존 업로드 주소가 설정된 단일 `index.html`입니다. 기존 촬영 사이트의 같은 HTTPS 주소에 교체 배포합니다. 이 파일을 만든 것만으로 운영 사이트나 Apps Script가 바뀌지는 않습니다.

## 달라진 사용 흐름

1. 네 컷을 촬영하면 원본 네 장·최종 JPG·접수번호·디자인을 이 기기의 브라우저 저장소에 보관합니다.
2. ‘이 사진으로 접수’를 누르면 같은 사진·번호로 전송합니다. 전송 중에도 ‘사진 보관하고 다음 팀’을 눌러 다음 촬영을 시작할 수 있습니다.
3. 상단 ‘이 기기의 보관 사진’에서 실패 건을 열거나 JPG를 저장하고 같은 사진을 재전송합니다. 미접수 초안은 ‘사진 열기’ 후 접수 버튼을 눌러야 전송됩니다.
4. 접수가 확인되면 브라우저 저장소에서 해당 사진·원본·전송 데이터를 지우고 접수번호 기록만 남깁니다. 드라이브의 사진은 지우지 않습니다.
5. 새로고침 뒤에는 보관 목록이 펼쳐집니다. 전송 도중 닫힌 건도 같은 번호·같은 사진으로 재전송할 수 있습니다. 서버의 중복 방지를 이용합니다.

한 컷 재촬영과 디자인 변경은 미접수 초안에서 사용할 수 있습니다. 이미 접수 요청을 보낸 사진은 저장 내용이 바뀌지 않도록 편집을 잠급니다.

## 사진을 지우거나 복구할 때

- ‘사진 지우고 처음으로’는 확인창을 거쳐 현재 팀의 기기 보관 사진을 지웁니다.
- ‘사진 보관하고 다음 팀’은 보관 기록을 확인한 후 다음 팀으로 넘어갑니다.
- ‘기기에서 삭제’는 선택한 로컬 사진을 지웁니다. 이미 서버에 저장된 사진이나 드라이브 파일을 삭제하는 기능이 아닙니다.
- 현재 사진을 열어둔 상태에서는 다른 보관 사진을 열 수 없습니다. 현재 사진을 보관하고 다음 팀 화면으로 돌아간 뒤 목록에서 엽니다.
- 카메라 권한 대기 중에도 ‘처음으로/기존 사진으로 돌아가기’로 취소할 수 있습니다. 취소한 요청이 뒤늦게 허용되어도 그 카메라 스트림은 즉시 종료합니다.

## 보관 범위와 기간

보관은 **동일 기기·동일 브라우저 프로필·동일 사이트 주소(프로토콜/호스트/포트)** 안에서만 복구됩니다. 다른 크롬북, 다른 계정/프로필, 시크릿·게스트 세션으로 옮겨지지 않습니다. 브라우저 데이터 삭제, 학교 기기 정책에 따른 초기화, 저장소 정리까지 견디는 백업은 아닙니다. 네트워크가 불안정하면 JPG도 별도로 저장하세요.

- 미접수/응답 불명 사진: 자동 삭제하지 않습니다. 24시간이 지나면 정리 안내가 표시됩니다. 행사 종료 후 담당자가 접수 여부를 확인하고 삭제합니다.
- 접수 확인된 사진: 브라우저 저장소의 이미지 데이터 즉시 삭제. 현재 완료 화면의 다운로드용 메모리는 ‘다음 팀’ 또는 페이지 종료 때 정리됩니다.
- 사진 없는 접수번호 기록: 24시간 보관 후 목록 새로고침/다음 실행 시 정리됩니다.
- 저장 공간이 부족하거나 저장소를 열 수 없으면 다음 팀 진행·전송을 막고 사진 다운로드를 유지합니다. 기기에 저장했다고 표시되지 않은 사진은 복구를 보장하지 않습니다.

## 전송 대기 목록

전송은 한 번에 한 건씩 처리합니다. 같은 브라우저의 여러 탭은 Web Locks로 동시에 보내지 않도록 막습니다. 다른 탭이 보내고 있다면 목록을 새로고침하고 필요 시 재전송합니다. 실제 부스에서는 탭 하나를 사용하세요.

전송 중 다음 팀을 찍어도 이전 팀의 완료 응답이 새 팀 화면을 바꾸지 않습니다. 페이지를 닫으면 전송 작업은 중단되지만 기기 보관 기록은 남습니다. 다시 연 뒤 재전송 버튼을 누르세요. 인터넷 복구 후 자동 전송하거나 브라우저를 닫은 상태에서 전송하는 기능은 없습니다.

기기 저장소가 없는 예시 모드는 기존처럼 디자인 비교와 다운로드만 제공합니다. 예시 이미지는 보관/접수하지 않습니다.

## 서버와 배포

- 기존 Apps Script 주소와 행사 코드 `BOKJEONG-2026`, 6자리 접수번호 규약을 유지했습니다.
- 서버 교체 없이 기존 접수 형식으로 전송합니다. 이전 연결판에서 실제 서버 접수/중복 재전송이 확인되었습니다.
- v1.4에서는 추가 실제 서버 사진을 올리지 않고 복구·동시 처리·실패 경로를 모의 서버로 검증했습니다.
- 앞서 전달한 `history4cut_server_patch.zip`의 서버 예외 처리 보완은 별도입니다. 실제 서버에는 아직 적용하지 않았습니다.
- 같은 사이트에서 행사 코드/접수 서버를 바꾸기 전에는 보관 사진을 모두 접수 또는 다운로드하세요. 접수 주소가 다른 보관 요청은 자동 전송하지 않습니다.
- 출력은 현재 900×2700px(1:3)입니다. 세 디자인과 상단 AI 생성 삽화·텍스트 렌더링은 유지했습니다.

## 크롬북에서 확인할 것

1. 새 HTTPS 파일을 열고 카메라 권한 대기 취소와 다시 연결을 확인합니다.
2. 한 팀 촬영 → 보관하고 다음 팀 → 새로고침 → 사진 열기로 원본 네 장을 확인합니다.
3. 인터넷을 끊은 상태에서 접수 → 다음 팀 촬영 → 인터넷 복구 후 대기 사진 재전송을 확인합니다.
4. 완료 번호와 드라이브 사진/운영대장 기록이 일치하는지 확인합니다.
5. 여러 크롬북의 부스 주소 `?booth=B1`, `?booth=B2`, `?booth=B3`에서 동시 접수합니다.

실제 크롬북의 학교 관리 정책·저장 공간·카메라·네트워크는 아직 검증하지 않았습니다.
